# 14 — Решения и обоснования

Формат: ID · статус (ACCEPTED / PROPOSED / NEEDS_USER / SUPERSEDED) · решение · обоснование · следствия. Изменение решения — новая запись со ссылкой на старую (старая → SUPERSEDED с причиной).

### D-001 Ponytail full — как принцип, а не сокращение объёма · ACCEPTED (2026-10-21)
- **Решение**: оба агента используют Ponytail уровня full (закреплённая копия, commit `df9e8994…`). Применяется к *способу* решения: минимальный код, без лишних абстракций, универсальных подсистем и «на будущее», переиспользование имеющегося, тест к нетривиальной логике.
- **Не разрешает**: сокращать объём проекта, упрощать оригинальное поведение, пропускать проверки, ослаблять совместимость с оригиналом или поддержку трёх ОС. В терминах Ponytail это «anything the user asked for» — никогда не срезается.
- **Следствия**: крейты/системы создаются вместе с первой задачей, которой они нужны (`04-architecture.md` §2); зависимости — только после проверки `17-dependencies.md` §1.

### D-002 Целевая сборка — Steam PC build 257 / CL 2863302 · ACCEPTED
- Хеш exe `1231B384…4C17` (`00-scope.md` §4). Другие издания не смешиваются. Steam buildid этой сборки — 9218157 (E-045).

### D-003 Bevy 0.20.0, точный pin · PROPOSED (подтверждается в T-050)
- Последняя стабильная (2026-10-08), MSRV 1.97.1, локальный rustc 1.99.1. Минимальный набор features; аудит C-зависимостей. Повышение версии — отдельное решение.

### D-004 Координаты UE3 в симуляции · ACCEPTED
- Симуляция в единицах и осях UE3 (`f32`, Z-up, левосторонняя; ротаторы `i32` 16-битных единиц угла); преобразование в систему Bevy только в слое представления. Причина — побитовое совпадение арифметики с оригиналом.

### D-005 Скрипты не исполняются; данные-графы интерпретируются · ACCEPTED
- UnrealScript-байткод и нативный код оригинала в runtime не исполняются и не транслируются автоматически. Поведение переписывается в Rust по декомпиляции.
- Данные уровней и определений, включая Kismet-последовательности и Behavior-графы (связи узлов и их параметры — это контент, как геометрия), читаются и интерпретируются Rust-кодом; *каждый тип узла* реализован в Rust вручную.
- Исследовательские инструменты (декомпилятор байткода) допустимы и не входят в runtime.

### D-006 Детерминированность оригинала не предполагается · ACCEPTED
- Новая реализация делает все источники изменчивости явными входами (dt, ввод, RNG, сеть). Сравнение — через записи оригинала и калибровку его разброса (`10-validation.md`).

### D-007 Модель float · ACCEPTED (2026-10-22, T-011, E-023)
- Игровая математика — `f32` IEEE single с округлением к ближайшему чётному, без FTZ/DAZ (как MXCSR по умолчанию в оригинале); порядок операций и ассоциативность — как в исходной функции (в т.ч. порядок сумм в `VSize` y²+x²+z², векторные операции packed SSE — по полосам); места с `double` в оригинале считаются в `f64`.
- Преобразования float→int повторяют SSE: `cvttss2si` (усечение) и `cvtss2si` (к чётному) с результатом 0x80000000 при NaN/переполнении — одной функцией-помощником в `bl2-sim`, не `as i32`. `Round/FFloor/FCeil` — формулы E-023.
- `RSQRTSS` (VRand, траектории) зависит от CPU и в оригинале: эмулировать табличное приближение одного вендора (выбор и проверка — при переносе VRand/T-060; R-18). Трансцендентные функции — реализации, повторяющие MSVCR100 `__libm_sse2_*`, проверяются на векторах из оригинала.
- Код с x87 (`FLDCW`, `_CI*`) переносится по отдельности после проверки точности конкретной функции (по умолчанию x87 53 бита, D3D9 с FPU_PRESERVE — E-023).

### D-008 Материалы — перевод байткода SM3 оригинала в WGSL · ACCEPTED (2026-10-22, T-019)
- См. `08-rendering.md` §2. Основание подтверждено E-030: байткод `vs_3_0`/`ps_3_0` есть для всех 83 026 шейдеров материалов и 251 из 253 глобальных; источник для каждого материала — карта в `RefShaderCache` по GUID из его нативного хвоста. Исключение: 2 Bink-шейдера без байткода — WGSL по открытому `Engine/Shaders/BinkShaders.usf` (путь 3). Транслятор D3D9 bytecode → WGSL и привязка констант — T-082/T-038; если там выяснится, что перевод невозможен для части шейдеров, решение пересматривается для них. **Дополнение 2026-10-23 (E-068)**: для 8 105 MIC набора статических параметров нет в `RefShaderCache` — оригинал компилирует их во время игры из графа материала и `.usf`; для них путь — собственная генерация по алгоритму компилятора материалов оригинала (T-038a), не байткод.

### D-009 Физика тел · PROPOSED (уточнено 2026-10-23 по E-033; окончательно — после проверки веток `Behavior_PhysXLevel` и рэгдоллов, T-022)
- Собственные UE3-запросы коллизий для движения и трасс (включая хитбоксы `PhysicsAsset`) — обязательно.
- Влияющее на логику (E-033): транспорт, лут до засыпания, KActor/KAsset и импульсы — собственная реализация модели rigid body по поведению PhysX 2.8 оригинала с проверкой траекторий/итоговых позиций против записи оригинала (T-017); для сети достаточно тех же реплицируемых полей и авторитета сервера (T-092).
- Только визуальное (ткань, частицы PhysX, жидкости, силовые поля, APEX, рэгдолл — если подтвердится): чисто-Rust приближение допускается при визуальном соответствии (`10-validation.md`).
- Ветвления по `PhysXLevel` воспроизводятся как в оригинале для каждого уровня настройки.

### D-010 Steam — единственное исключение, опциональное · ACCEPTED (решение пользователя, 2026-10-21)
- **Решение пользователя**: библиотека Steam API от Valve — **единственное** разрешённое исключение из правила «runtime только на Rust». Она **опциональна**: если библиотека доступна — игра через Steam (онлайн-сессии, совместимые с оригиналом); если нет — только LAN. Код Valve не обязателен для сборки и работы игры.
- **Реализация (уточнено 2026-10-21 по результатам E-052…E-055)**:
  - `steam_api` заменяется **собственным Rust-кодом**: `steam_api.dll` BL2 — лишь тонкий загрузчик (читает `HKCU\Software\Valve\Steam\ActiveProcess\SteamClientDll64`, загружает клиент Steam, `CreateInterface("SteamClient012")`, получает интерфейсы, опрашивает колбэки через экспорты `Steam_BGetCallback`/`Steam_FreeLastCallback`) — E-053. Это же делает наш модуль `bl2-net/steam.rs`.
  - Единственный загружаемый код Valve — **клиент Steam, уже установленный у пользователя**: `steamclient64.dll` (Windows; путь из реестра `ActiveProcess`), на Linux/macOS — аналоги из установки Steam (пути — HYPOTHESIS, исследовать после D-014). `steam_api64`/Steamworks SDK **не нужны**: не надо ни получать, ни распространять, ни линковать.
  - Используются те же версии интерфейсов, что у оригинала (`SteamClient012`, `SteamNetworking005`, `SteamMatchMaking009`, `SteamUser016`, `SteamFriends013`, `SteamUtils005`, `SteamGameServer011`, …) — E-053; текущий `steamclient64` их предоставляет (E-054). AppID — 49520 (через `SteamAppId`/`SteamGameId`, как делает `steam_api`).
  - Нет клиента Steam / не запущен / `ConnectToGlobalUser` = 0 / интерфейс не получен → только LAN, онлайн-пункт скрыт, причина в логе.
  - Весь код, вызывающий Steam, — в одном модуле `bl2-net/steam.rs`; протокол UE3 и репликация — общие для LAN и Steam.
  - Аудит runtime (`10-validation.md` §7, `17-dependencies.md` §3) допускает ровно один не-Rust код не-ОС: клиент Steam Valve (`steamclient64` и загружаемые им модули), и только в Steam-режиме.
- **Проверено** (E-055): 64-битная Rust-программа без зависимостей и без `steam_api` получила `SteamNetworking005`, `GetAppID` = 49520, `BLoggedOn` = true. **Не проверено**: обмен P2P-пакетами с оригиналом (нужны слоты методов `ISteamNetworking005` и реальная сессия) — T-095.

### D-014 Linux и macOS — после готовности Windows-реализации · ACCEPTED (решение пользователя, 2026-10-21)
- **Решение**: работы и проверки на Linux/macOS (T-100…T-103, матрица `16-platforms.md` §4, сетевые ячейки N-1 с этими ОС) не начинаются, пока реализация на Windows не пройдёт приёмку по Windows-части `10-validation.md` (этап M8-W, `11-roadmap.md`).
- **Не меняет требований**: поддержка трёх ОС остаётся обязательной (R-3, R-8). Поэтому уже сейчас: общий код (`bl2-formats`, `bl2-sim`, `bl2-net`, `bl2-render`) не содержит Windows-специфики; пути — через резолвер (`06-assets.md` §3), каталоги — через одну функцию (`16-platforms.md` §3); новые зависимости проверяются на поддержку трёх ОС (`17-dependencies.md` §1, п.3) — это проверяется чтением кода/документации, без запуска на этих ОС.
- **Допустимо без нарушения решения**: компиляционная проверка `cargo check --target x86_64-unknown-linux-gnu` — только если не требует установки чего-либо вне рабочей директории; результат помечается «кросс-проверка», не статус платформы. По умолчанию — не делать.

### D-015 Источники оригинала: копия проекта и Steam-установка · ACCEPTED
- Копия `D:\Projects\bl2-rs\Borderlands 2` — для чтения данных, тестов (`BL2_INSTALL`) и статического анализа.
- Steam-установка `D:\SteamLibrary\steamapps\common\Borderlands 2` (buildid 9218157, тот же exe, E-045) — для запуска оригинала через Steam и записей поведения. Её файлы не изменять; инструментирование — внешними средствами.
- Идентичность двух каталогов — E-049. При любом обновлении игры Steam (смена buildid или хеша exe) — остановить сравнительные проверки и зафиксировать новую сборку отдельно (D-002), не смешивая результаты. Автообновление игры в Steam рекомендуется отключить (вопрос пользователю, если buildid изменится).
- Пользовательские данные оригинала читаются только из копий в `.research/user-data/<дата>/`.

### D-016 Второй экземпляр оригинала — в пределах рабочей машины · ACCEPTED (по ответу пользователя «делай что нужно в пределах рабочей директории»)
- Для сетевых экспериментов используются два экземпляра на этой машине: Steam-установка (запуск через Steam) и копия проекта (запуск `Borderlands2.exe` напрямую; `steam_appid.txt` присутствует). Возможность LAN-сессии двух экземпляров под одним Steam-аккаунтом — UNKNOWN (E-UNK-14), проверяется первым шагом T-018. Если невозможно — блокер B-04 возвращается с точным описанием, что требуется (второй аккаунт/вторая машина).
- Захват трафика на одной машине: петлевой интерфейс (Npcap loopback adapter) — установка Wireshark/Npcap выходит за рабочую директорию → требует согласия пользователя (вопрос в T-018).

### D-017 Теги свойств, отсутствующих в runtime-схеме · ACCEPTED (2026-10-22, T-032a)
- Критерий T-032a «100 % тегов типизированы» применяется к свойствам, которые есть в runtime-классах (скриптовая схема E-063). Теги свойств, которых в схеме нет (editor-only данные в cooked-пакетах), декодируются, если тип следует из самого тега (скаляры, структуры), иначе (массивы — тип элемента нигде не записан) хранятся как `Value::Untyped` с диапазоном байт и точным счётчиком (E-064). Runtime их не загружает в объекты: у класса нет такого свойства. Не угадывать тип элемента по размеру.

### D-013 Хранение доказательств · ACCEPTED
- В репозитории — метаданные и выводы; производные от кода/ассетов оригинала — только в `.research/` (локально, не коммитится).

Уточнение реализации 2026-10-22 (T-016, E-027): переносится только доказанная оболочка сохранений; непрочитанный payload остаётся непрозрачным. Лимит распаковки задаёт вызывающий код. Новых зависимостей и изменений решений об исполнении оригинала нет. T-013: после исправления E-025 схема расписания остаётся частично HYPOTHESIS до исследования акторского слота +0x1f4 и таймеров.
