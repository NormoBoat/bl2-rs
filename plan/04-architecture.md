# 04 — Архитектура Rust + Bevy ECS

Принцип (Ponytail full, D-001): строить только то, что нужно игре. Крейты, системы и абстракции появляются вместе с первой задачей, которой они нужны; ниже — целевая форма и правила, а не список того, что надо создать заранее.

## 1. Основные решения

| Вопрос | Решение | Обоснование / статус |
|---|---|---|
| Версия Bevy | 0.20.0 (точный pin `=0.20.0`) | Последняя стабильная на 2026-10-21 (crates.io, выпущена 2026-10-08, MSRV 1.97.1 ≤ rustc 1.99.1). Обновление только отдельным решением в `14-decisions.md`. Проверка сборки на трёх ОС — T-030 (D-003) |
| Координаты симуляции | Координаты UE3 как есть: `f32`-вектор, левосторонняя система, Z вверх, единицы — Unreal Units; ротаторы — `i32` Pitch/Yaw/Roll (65536 = 360°) | Совпадение арифметики с оригиналом. Конверсия в систему Bevy (правосторонняя, Y вверх) — только в слое представления (D-004). Масштаб uu↔метр для звука/рендера — UNKNOWN (E-UNK-03) |
| Время | Тик симуляции с переменным `DeltaSeconds`, как в UE3, источник dt абстрагирован ресурсом `SimClock` (реальные часы / записанная последовательность dt / фиксированный шаг для сервера) | UE3 тикает с переменным dt и сглаживанием кадра (`bSmoothFrameRate`, `MaxSmoothedFrameRate=62` в одной секции, `120`/FALSE в другой — E-008). Для сравнения с оригиналом нужен replay записанных dt. Детерминированность оригинала **не предполагается** (D-006) |
| RNG | Точная реплика генераторов оригинала (E-024): CRT `rand` MSVCR100 (один на поток, сид при старте), второй глобальный LCG (×196314165) и сиды объектов; `bl2-sim::rng`. `-FIXEDSEED` оригинала даёт сид 0 обоим — режим сравнения записей | Совпадение лута/урона/AI при одинаковом сиде |
| Арифметика | `f32` с SSE; если оригинал использует x87 с 80-битными промежуточными значениями (T-011), критичные функции воспроизводить с явной моделью округления | E-UNK-01 |
| Порядок обновления | Расписание Bevy повторяет группы тиков UE3 (`TG_PreAsyncWork`, `TG_DuringAsyncWork`, `TG_PostAsyncWork`, `TG_PostUpdateWork`, …) и порядок акторов внутри группы | HYPOTHESIS: стандартный UE3 `UWorld::Tick`; подтвердить декомпиляцией (T-013) |
| Скрипты | UnrealScript не исполняется. Поведение классов переносится в Rust-системы вручную по декомпилированному байткоду и нативному коду | D-005 |
| Данные-графы (Kismet, Behavior-провайдеры BL2) | Читаются как данные; каждый тип узла реализован в Rust | D-005 |
| Headless | Один и тот же код симуляции работает без окна/GPU/аудио (`MinimalPlugins` + собственные плагины симуляции); используется для выделенного хоста проверок, тестов, replay | Требование задачи; T-050 |

## 2. Крейты (целевая форма; создаются по мере надобности)

```
crates/
  bl2-formats    чтение установки: пакеты UE3, LZO, имена/импорт/экспорт, свойства, TFC, локализация, ini.
                 Без Bevy. Используется и runtime, и исследовательскими утилитами.
  bl2-sim        игровая симуляция: компоненты, ресурсы, системы, расписание тиков. Без рендера/окна/звука.
  bl2-net        протокол UE3/BL2: пакеты, каналы, bunch, репликация, RPC, LAN-обнаружение.
  bl2-render     материалы (перевод шейдеров), проходы, постобработка, UI-рендер. Зависит от Bevy render.
  bl2-audio      декодирование и воспроизведение аудио-банков (формат — T-020).
  bl2-ui         рантайм UI (подмножество Scaleform/Flash, нужное игре — T-021).
apps/
  bl2            исполняемый файл игры (клиент/listen-хост).
  bl2-headless   выделенный headless-хост и replay-раннер для проверок.
tools/
  research/      скрипты исследования (любой язык).
  bl2-dump       Rust-утилита дампа пакетов/скриптов/шейдеров поверх bl2-formats (по мере надобности).
```

Правило зависимостей: `bl2-formats` ← `bl2-sim` ← (`bl2-net`, `bl2-render`, `bl2-audio`, `bl2-ui`) ← `apps/*`. `bl2-sim` не зависит от рендера, окна и аудио — это обеспечивает headless и общую логику для трёх ОС.

Первый шаг (T-030) — только `crates/bl2-formats` и минимальный workspace; остальные крейты появляются в задачах, которым они нужны.

## 3. Отображение объектной модели UE3 на ECS

| UE3 | ECS | Примечания |
|---|---|---|
| Пакет, экспорт, импорт | `bl2-formats` структуры; загруженные определения — `Resource`/`Asset`-хранилище по `ObjectPath` | Стабильный ключ — полный путь объекта (`Package.Group.Name`) + класс |
| `UObject`-определения (GD_*-данные: Balance, ItemPool, WeaponPartDefinition, AttributeDefinition, Behavior…) | Неизменяемые Rust-структуры в хранилище определений (`Res<Definitions>`), ссылки — типизированные хэндлы | Загружаются из пакетов, значения по умолчанию — из CDO классов (скриптовые пакеты) |
| `AActor` в мире | `Entity` + компоненты по иерархии класса (напр. `Pawn`, `WillowPawn`, `Weapon`, `Inventory`) | Наследование UE3 → набор компонентов; поведение — системы, фильтрующие по компонентам. Не делать универсального «объекта с vtable» |
| `UActorComponent` (`SkeletalMeshComponent`, `CylinderComponent`…) | Компоненты на той же или дочерней сущности | Иерархия `Attach` → `ChildOf` Bevy |
| Таймеры (`SetTimer`) | Компонент `Timers` + система в нужной группе тиков | Порядок срабатывания — как в оригинале (T-013) |
| Состояния UnrealScript (`state`/`GotoState`) | `enum`-компонент состояния + системы по состояниям | |
| Латентные функции (`Sleep`, `FinishAnim`, `MoveTo`) | Явные машины состояний в компоненте | |
| События (`Touch`, `TakeDamage`, `Died`) | Bevy-события/observers с контролируемым порядком | Порядок доставки — исследовать для каждого |
| Kismet `SequenceObject`, Behavior-графы BL2 | Данные + интерпретатор узлов в Rust | D-005 |
| Репликация (`RemoteRole`, `bNetDirty`, `NetIndex`) | Компоненты `NetId`, `NetRole`, реплицируемые поля как отдельные компоненты/структуры с порядком полей, совпадающим с оригиналом | `09-network.md` |

## 3a. Жизненный цикл объектов

- Размещённые в карте акторы создаются при загрузке уровня (в порядке экспортов пакета — HYPOTHESIS, проверить T-037/T-051), вызовы инициализации (`PreBeginPlay`/`PostBeginPlay`/`BeginPlay`-эквиваленты) — в том порядке, что в оригинале (T-013).
- Spawn во время игры: создание сущности сразу (как `SpawnActor` в UE3 — синхронно, актор доступен в том же тике), события инициализации — в тот же тик.
- Destroy: в UE3 актор помечается и ссылки на него становятся недействительными сразу, память освобождается позже. В ECS: компонент-метка `PendingDestroy` в момент `Destroy`, реальное `despawn` — в конце тика; системы игнорируют помеченные сущности. Точный момент недоступности ссылок — исследовать (T-013).
- Выгрузка streaming-уровня уничтожает его акторы (и сетевые каналы к ним) — порядок как в оригинале (T-069).
- Сетевые акторы на клиенте создаются/уничтожаются по открытию/закрытию акторного канала (`09-network.md` §3.4).

## 4. Идентификаторы

- **Определения**: `ObjectPath` (строка, регистр нечувствителен как в UE3 `FName`), внутри процесса — интернированный индекс.
- **Акторы мира**: `ActorId` = (уровень, индекс экспорта) для размещённых в карте; для заспавненных — монотонный счётчик. Не использовать `Entity` Bevy как игровой или сетевой ID.
- **Сеть**: `NetIndex` и/или индексы каналов UE3 — как в оригинальном протоколе (`09-network.md` §3). Для статических акторов уровня — тот же способ сопоставления, что использует оригинал (исследовать: UE3 использует `NetIndex` из пакета уровня — HYPOTHESIS).
- **Сохранения**: идентификаторы предметов/миссий — в виде, принятом форматом сохранений (`07-gameplay.md` §6).

## 5. Расписание (Bevy)

```
Startup: загрузка установки (проверка манифеста) → регистрация определений
FixedMain не используется для игровой логики (dt переменный); собственный schedule `SimTick`, запускаемый из `Update` N раз с dt из SimClock:
  SimTick:
    NetReceive            (bl2-net: приём, применение реплицированного состояния / RPC)
    Input                 (ввод → PlayerInput как в UE3: aBaseX/aForward…)
    TG_PreAsyncWork       (акторы: Tick, физика движения Pawn, контроллеры, AI)
    TG_DuringAsyncWork    (физика тел — по результатам T-022)
    TG_PostAsyncWork
    TG_PostUpdateWork     (камера, вложения)
    TG_EffectsUpdateWork  (эффекты; E-025)
    Timers / Latent
    NetSend               (репликация по NetUpdateFrequency/приоритетам)
PostUpdate: синхронизация представления (Transform из координат UE3), анимация-поза, звук, UI
Render: Bevy render app (bl2-render)
```

Статически установлено (E-025): фазы движка — Client.Tick → тикаемые объекты → seamless travel → `UWorld::Tick` → viewports → travel/pending level → отрисовка → level streaming → звук → streaming manager; в `UWorld::Tick` — demo/net dispatch, RealTime/AudioTime, `dt *= TimeDilation`, `clamp(dt, 0.0005, 0.4)`, затем 5 групп TG_PreAsyncWork…TG_EffectsUpdateWork (добавлена TG_EffectsUpdateWork). Остальной состав (физика, таймеры, сеть внутри `UWorld::Tick`) — HYPOTHESIS до завершения T-013; изменения фиксировать в `14-decisions.md`.

## 6. Разделение слоёв

Уточнение E-025 (2026-10-22): в TG1…TG4 компоненты обрабатываются также непосредственно после своего актора, а компоненты будущих групп откладываются. Групповой вызов актора — слот +0x1f4; +0x3bc в 0x6adda0 относится к отдельной операции. Схема выше пока не задаёт полного порядка систем; не реализовывать её как «все акторы, затем все компоненты».

- **Симуляция** (`bl2-sim`): только данные и системы игрового состояния; детерминированна относительно (начальное состояние, последовательность dt, вход, сиды RNG, входящие пакеты).
- **Представление**: меши, материалы, частицы, звук, UI читают состояние симуляции; не меняют его. Исключение — то, что в оригинале влияет на логику (напр., анимационные уведомления `AnimNotify`, root motion, физика рэгдоллов, если влияет): такие места выявляются исследованием и переносятся в симуляцию явно.
- **Платформенный ввод**: winit/gilrs → нормализованные события → `PlayerInput`. Привязки — из `DefaultInput.ini` оригинала.

## 7. Загрузка ресурсов и связь с ECS

- Путь к установке задаёт пользователь (аргумент/конфиг); проверка — `06-assets.md` §4.
- Пакеты читаются лениво; объекты из пакета превращаются в Rust-определения и ассеты Bevy (`Image`, `Mesh`, собственные ассеты материалов/анимаций).
- Уровень: persistent `*_P.upk` + streaming-уровни (`LevelStreaming` из данных); загрузка/выгрузка — по правилам оригинала (триггеры streaming-объёмов, `07-gameplay.md`).
- Кеш преобразованных данных — `06-assets.md` §5.

## 8. Headless

`apps/bl2-headless`: `MinimalPlugins` + `bl2-sim` + `bl2-net`, без окна/GPU/аудио. Используется для (1) сетевого хоста в проверках, (2) replay-сравнения с записями оригинала, (3) CI. Любая логика, которая нужна хосту, обязана жить в `bl2-sim`, а не в рендере.
