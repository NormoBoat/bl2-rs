# 08 — Графика и визуальное соответствие

Цель — воспроизвести **видимый результат** оригинала, а не просто загрузить модели.

## 1. Что известно об оригинальном рендере (E-010, E-018)

- ПК-рендер — Direct3D 9: строки `d3d9.dll`, `d3dx9_43.dll`, `Direct3DCreate9`, `GetD3D9CubeFace`; глобальный кеш шейдеров `GlobalShaderCache-PC-D3D-SM3.bin` (Shader Model 3). Из D3D11 в exe найдена только UTF-16 строка `AllowD3D11` — D3D11-пути нет: импорты — только `d3d9.dll`/`d3dx9_43.dll` (E-030).
- В установке есть **исходники шейдеров UE3** (`Engine/Shaders/*.usf`, 163 файла), в том числе Gearbox-специфичные: `EdgeDetectionPostProcessBlend*` (контурные линии «cel-shading» — HYPOTHESIS по названию), `GBXShadowProjection*`, `Grendel_Shadow*`, `ItemCardThumbnail*`, `UberPostProcessBlendPixelShader`, `DOFAndBloom*`, `FXAA*`, `TemporalAA*`, `SSAO`, `LUTBlender`, `HeightFog*`, `FogVolume*`, `LightShaftShader`, `SpeedTree*`, `GFx*` (Scaleform), `BinkShaders`.
- `GlobalShaderCache-PC-D3D-SM3.bin` содержит D3D9 `vs_3_0`/`ps_3_0` байткод; `Engine/Shaders/Patched/VoG{A,B,C}.bin` (по 2 700 байт) — отдельные `ps_3_0` шейдеры с таблицей констант `CTAB`, назначение UNKNOWN (E-043). Наличие SM3-байткода в кеше — основание для D-008; для материалов уровня (кеши в пакетах) — проверить в T-019.

## 2. Стратегия материалов (решение D-008, ACCEPTED по E-030)

Порядок предпочтения:

1. **Перевод скомпилированного байткода SM3 оригинала → WGSL** (собственный транслятор на Rust, офлайн при построении кеша). Даёт ту же математику, что видит GPU в оригинале, включая константы и сгенерированный код материалов. Кеши найдены и разобраны (E-030: `RefShaderCache-PC-D3D-SM3.upk`, `crates/bl2-formats/src/shader_cache.rs`). Требует: разобрать D3D9 bytecode, сопоставить регистры констант с параметрами, которые выставляет рендер (из декомпиляции exe).
2. **Генерация из графа выражений материала** по `MaterialTemplate.usf` — если байткода нет для каких-то материалов/перестановок.
3. Ручная реализация в WGSL — только для глобальных шейдеров, если перевод невозможен; со сверкой по кадрам.

Почему не Bevy `StandardMaterial`: модель освещения UE3 (lightmaps, light environments, модулированные тени, специфический specular) отличается; PBR Bevy не даст совпадения.

## 3. Что даёт Bevy и что пишем сами

| Область | Bevy (0.20) | Пишем на Rust / WGSL |
|---|---|---|
| Окно, swapchain, GPU API | `bevy_winit`, `bevy_render` (wgpu: DX12/Vulkan/Metal) | — |
| Ассеты GPU (меши, текстуры) | `Mesh`, `Image`, загрузка в GPU | Конвертеры из форматов UE3 (S-01); BCn-форматы — проверка поддержки на каждой платформе (на Apple GPU BC может отсутствовать на iOS-классе; на Mac — поддерживается, проверить, `16-platforms.md`) |
| Камера, видимость | `Camera`, frustum culling | FOV/проекция UE3, precomputed visibility, если используется |
| Материалы | Пайплайны, bind groups, `Material`-трейт или собственные render-nodes | Транслятор SM3→WGSL, параметры материалов, инстансы |
| Освещение | — (PBR Bevy не используется) | Lightmaps/shadowmaps из пакетов, `DynamicLightEnvironment`, точечные/прожекторные/направленные источники как в UE3 |
| Тени | — | Проекции теней как `ShadowProjection*`/`GBXShadowProjection*`/`Grendel_*` |
| Постобработка | Render graph | Цепочка из `PostProcessChain` оригинала: bloom/DOF, uber post, edge detection (контуры), FXAA, gamma/LUT, motion blur — порядок и параметры из данных |
| Скелетная анимация | `bevy_animation` — только как контейнер, если подходит | Декодирование сжатых анимаций UE3, блендинг AnimTree, морфы — по коду оригинала; позы считаются на CPU/GPU как в оригинале (GPU skin — `GpuSkinVertexFactory.usf`) |
| Частицы | — | Cascade-эмиттеры (спрайты, ленты/beam/trail, меш-частицы), сортировка прозрачности |
| UI | `bevy_ui` не используется для игрового UI | Рендер Scaleform-векторной графики (`GFxPixelShader.usf`, `GFxVertexShader.usf`), шрифты |
| Видео | — | Bink-декодер → текстура (`BinkShaders.usf`) |

## 3a. Геометрия, координаты, единицы, цвет

- Мир хранится в координатах UE3 (D-004). Преобразование в Bevy: `(x, y, z)_UE → (x, z, -y)` или иное — выбрать одну формулу при T-051 и проверить на кадре (ручность системы, направление вращений, порядок углов Pitch/Yaw/Roll ротатора UE3). Масштаб — 1 uu = 1 единица рендера (метры не нужны рендеру; E-UNK-03 важен для звука/физики).
- Проекция: горизонтальный FOV UE3 (по умолчанию из конфигов/`WillowPlayerController` — уточнить), near-plane и обратный/прямой Z — как требует перевод шейдеров (D3D9 depth 0..1 совпадает с wgpu).
- Нормали/тангенты: упаковка вершинных атрибутов UE3 (packed normals) распаковывается в шейдере как в оригинальном vertex factory.
- Цвет: в D3D9 sRGB-чтение/запись управлялись состояниями сэмплеров/рендер-таргетов (`SRGBTexture`, `SRGBWriteEnable`) — извлечь, какие текстуры/цели sRGB (T-019/T-080); гамма-коррекция `GammaCorrectionPixelShader.usf`, LUT `LUTBlender.usf`; HDR-формат промежуточных целей — как в оригинале (D3D9 SM3 PC: вероятно, RGBA16F или «RGBE-кодирование» — UNKNOWN). Ошибка в sRGB видна на всех кадрах — проверяется первой.

## 4. Эталонная конфигурация для сравнения

- Разрешение 1920×1080, оконный режим без масштабирования, полный набор настроек оригинала зафиксирован файлами конфигурации пользователя (после первого запуска: `Documents/My Games/Borderlands 2/WillowGame/Config/WillowEngine.ini` и др. — HYPOTHESIS пути, проверить в T-017); копия этих файлов хранится в `plan/evidence/raw/ref-config/` (конфиги — не ассеты).
- Сцены: список из ≥ 12 точек (по одной на тип окружения: снег, пустыня/пыль, интерьер, ночь/день, вода, растительность, город Sanctuary, DLC-локация, сцена с частицами боя, сцена с транспортом, меню, HUD с инвентарём).
- Камера: точная позиция/ротация, FOV; ставится одинаково в оригинале (консольные команды, если консоль доступна — UNKNOWN; иначе — инструментирование) и в новой реализации.
- Момент симуляции: фиксированное время суток/погоды; анимированные элементы — пауза/фиксированное время (как добиться в оригинале — исследовать в T-080).
- GPU: эталоны снимаются на одной машине; для оценки допусков — оригинал на двух разных GPU (разброс оригинала).

## 5. Критерии соответствия

Попиксельного равенства между разными GPU не обещаем. Метрики и допуски (окончательно калибруются в T-086 по разбросу оригинал↔оригинал на двух GPU; допуск = max(измеренный разброс × 1.5, нижние пороги ниже)):

| Метрика | Порог (стартовый) | Обоснование |
|---|---|---|
| Средняя ΔE2000 по кадру | ≤ 2.0 | Порог заметности ≈ 1–2.3 ΔE |
| 99-й перцентиль ΔE2000 | ≤ 10 | Допускает отличия растеризации на краях |
| SSIM (яркость) | ≥ 0.97 | Структурное совпадение |
| Доля пикселей с ΔE > 10 в маске объекта | ≤ 1 % для каждой маски | Ловит неверный материал на отдельном объекте, который не виден в среднем по кадру |
| Чек-лист эффектов | 100 % присутствуют | Контуры, bloom, DOF, туман, тени, частицы, декали, отражения, искажения, LUT — каждый проверяется отдельным кадром с эффектом и без (diff должен совпадать по форме) |

Допуски не должны скрывать отсутствующие эффекты: кроме общих метрик, каждый эффект проверяется отдельной парой кадров «эффект включён/выключен» в оригинале и в новой реализации, и разница этих пар сравнивается между реализациями.

Все визуальные расхождения регистрируются в `03-evidence.md` (DIVERGENCE-xxx) с кадрами в `.research/frames/` (кадры оригинала не коммитятся).

## 6. Настройки качества и платформы

- Настройки качества оригинала (текстуры, тени, AA, view distance, PhysX, ambient occlusion, depth of field, bullet decals, foliage, FOV) — перечень и влияние на рендер выяснить из конфигов и меню (T-080). Каждая настройка реализуется или явно отмечается как неприменимая с причиной.
- Различия платформ: wgpu-бэкенды (DX12/Vulkan/Metal) могут отличаться точностью/форматами; проверка по матрице `16-platforms.md` §4.
